6. Request Lifecycle

A single user objective — “Launch an AI SaaS in 90 days” — traced through every system component.

Step 1: API Gateway

POST /api/v1/objectives { raw_input: "Launch an AI SaaS in 90 days" }
  → Authenticate JWT
  → Validate input shape
  → Assign trace_id for observability
  → Dispatch to Objective Compiler

Step 2: Objective Compiler

Select LLM: o3-mini (reasoning task)
  → Inject system prompt + user input
  → Parse structured JSON against CompiledGoal schema
  → Store compiled objective in database
  → Emit event: objective.compiled
  → Return CompiledGoal to Kernel

Step 3: AI Kernel Dispatch

Receive CompiledGoal
  → Module Registry routes to Planner
  → Resource Allocator estimates compute needed
  → State Manager creates execution context
  → Forward goal to Planner

Step 4: Planner

Query Memory for similar past objectives
  → Select LLM: gpt-4o (complex planning)
  → Generate work streams with milestones & dependencies
  → Run PERT analysis for critical path
  → Identify bottlenecks (min 3)
  → Generate 2+ contingency plans
  → Return Plan to Kernel

Step 5: Parallel Dispatch

Kernel sends in parallel:
  → Plan to Org Generator (synthesize departments)
  → Plan to Risk Engine (assess risks)
  → Plan to Simulation Engine (compare strategies)

Step 6: Dashboard Assembly

Collect results from all parallel modules
  → Request Evidence Engine validate key claims
  → Check authority level for each decision
  → Create Decision records requiring human approval
  → Store complete state in Memory
  → Push dashboard via WebSocket

Step 7: Human Review

Dashboard renders: timeline, org graph, risks, comparisons
  → User reviews evidence, confidence, alternatives
  → User approves or rejects
  → POST /api/v1/decisions/:id/approve

Step 8: Execution

Kernel receives approval
  → Scheduler creates task queue
  → Dispatch tasks to agent departments
  → Agents execute (may request evidence, memory, tools)
  → On completion: Memory stores outcome

7. AI Kernel

The AI Kernel is the central nervous system of OrchestraOS. Seven subsystems operate inside it:

┌──────────────────────────────────────────────────────────────────┐ │ AI KERNEL │ │ │ │ ┌─────────────┐ ┌─────────────┐ ┌─────────────┐ │ │ │ Scheduler │ │ Memory │ │ Message │ │ │ │ • Priority Q │ │ Manager │ │ Bus │ │ │ │ • DAG resolver│ │ • Tiered │ │ • Pub/sub │ │ │ │ • Deadline │ │ storage │ │ • Routing │ │ │ │ tracking │ │ • Pruning │ │ • Delivery │ │ │ └──────┬───────┘ └──────┬──────┘ └──────┬──────┘ │ │ ┌──────┴───────┐ ┌──────┴──────┐ ┌──────┴──────┐ │ │ │ Module │ │ State │ │ Health │ │ │ │ Registry │ │ Manager │ │ Monitor │ │ │ └──────────────┘ └─────────────┘ └─────────────┘ │ │ ┌──────────────────────────────────────────────────────────┐ │ │ │ Resource Allocator │ │ │ │ • Token budget per module/provider │ │ │ │ • Model quota enforcement │ │ │ │ • Priority-based preemption │ │ │ └──────────────────────────────────────────────────────────┘ │ └──────────────────────────────────────────────────────────────────┘

7.1 Scheduler

Manages execution order with priority queuing and DAG-based dependency resolution. Priority levels: P0 (Critical), P1 (High), P2 (Normal), P3 (Low). Deadlock detection runs each cycle — breaks by escalating lowest-priority task.

7.2 Memory Manager

TierTechnologyCapacityEviction
HotRedis1GBLRU by importance score
Warmpgvector100K entriesImportance < 0.1 pruned
ColdPostgreSQL JSONUnlimitedArchived after 90 days

7.3 Message Bus

Reliable inter-module communication with pub/sub routing, at-least-once delivery guarantees, and dead-letter queues for failed deliveries.

7.4 Module Registry

Discovers, registers, and validates modules with interface versioning. Lifecycle: Register → Validate Interface → Health Check → Ready → Deregister.

7.5 State Manager

Maintains execution context per objective with snapshots for recovery and rollback. Supports concurrency control via per-objective locks.

7.6 Health Monitor

MetricSourceAlert Threshold
Module heartbeatModule ping (5s)Missed 3 pings = down
Task latencyExecution timer>2x expected duration
LLM error rateProvider wrapper>5% error rate
Memory utilizationMemory Manager>80% hot tier
Decision backlogDecision Surface>10 pending

7.7 Resource Allocator

Weighted fair queuing by objective priority. Burst allowance: 2x base for 60s. Starvation prevention: minimum 10% reserved for low-priority. Backpressure when >80% consumed.

12. Decision Flow

Every decision follows a formal lifecycle ensuring explainability and appropriate human oversight.

PROPOSE → GATHER EVIDENCE → RENDER (question, options, recommendation, confidence) → ROUTE (check authority level) ├── Auto-execute (high confidence, low risk) └── Human review → APPROVE / REJECT → EXECUTE → STORE MEMORY → LEARN (calibrate confidence)

12.1 Authority Level Determination

def determine_authority(confidence, risk_score, decision_type):
    if decision_type == "strategic":
        return "execute"          # Always human
    if risk_score > 0.7:
        return "execute"          # High risk = human
    if confidence < 0.6:
        return "approve"          # Low confidence = manager
    if confidence > 0.9 and risk_score < 0.3:
        return "recommend"        # High confidence, low risk = auto
    return "approve"

12.2 Decision Record Schema

{
  "decision_id": "dec_001",
  "question": "PostgreSQL or MongoDB?",
  "options": [{"id": "opt_a", "label": "PostgreSQL"}, {"id": "opt_b", "label": "MongoDB"}],
  "recommendation": {"option_id": "opt_a", "rationale": "...", "confidence": 0.88},
  "authority_required": "approve",
  "status": "pending"
}

13. Failure Handling

13.1 LLM Provider Failure

LLM call fails → Retry (backoff: 1s, 2s, 4s) → Fallback to next provider in chain → If all fail: return degraded (cached or simplified) response → Health Monitor updates error rate metric → If error rate > 5% in 5min → disable provider → auto-re-enable after cooldown

13.2 Module Failure

Detection: Heartbeat missed ≥3 checks (15s) or task >2x expected duration
Recovery: Mark unhealthy → restart from Module Registry
  → Restore state from snapshot → replay in-flight tasks
  → If restart fails ≥3 times → escalate to human

13.3 Agent Failure

Detection: Heartbeat + task timeout
Recovery: Log failure → retry on different agent
  → If no alternative → request Org Generator spawn
  → After 3 failures from same dept → trigger restructuring

15. Database Schema

15.1 Entity Relationship

organizations ─── users │ ├── objectives ─── plans ─── tasks │ │ │ decisions ─── evidence │ │ │ risk_assessments │ simulations │ decision_log (audit) │ ├── departments ─── agents ├── memory_entries (pgvector) └── organizational_health (time-series)

15.2 Core Tables

CREATE TABLE organizations (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    name VARCHAR(255) NOT NULL,
    slug VARCHAR(100) UNIQUE NOT NULL,
    plan_tier VARCHAR(50) DEFAULT 'starter',
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE objectives (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id UUID REFERENCES organizations(id) ON DELETE CASCADE,
    raw_input TEXT NOT NULL,
    compiled_spec JSONB,
    status VARCHAR(50) DEFAULT 'pending',
    trace_id VARCHAR(64),
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE plans (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    objective_id UUID REFERENCES objectives(id) ON DELETE CASCADE,
    plan_data JSONB NOT NULL,
    status VARCHAR(50) DEFAULT 'draft',
    version INT DEFAULT 1,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE decisions (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    objective_id UUID REFERENCES objectives(id) ON DELETE CASCADE,
    question TEXT NOT NULL,
    options JSONB DEFAULT '[]',
    recommendation JSONB,
    confidence DECIMAL(4,3),
    authority_level VARCHAR(50),
    status VARCHAR(50) DEFAULT 'pending',
    outcome VARCHAR(50),
    rejection_reason TEXT,
    resolved_by UUID REFERENCES users(id),
    resolved_at TIMESTAMPTZ,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

CREATE TABLE memory_entries (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    org_id UUID REFERENCES organizations(id) ON DELETE CASCADE,
    memory_type VARCHAR(50) NOT NULL,
    content TEXT NOT NULL,
    embedding VECTOR(1536),
    metadata JSONB DEFAULT '{}',
    importance DECIMAL(3,2) DEFAULT 0.5,
    created_at TIMESTAMPTZ DEFAULT NOW()
);

-- + departments, agents, tasks, evidence, risk_assessments, simulations,
--   organizational_health, decision_log (see .md for full definitions)

23. Observability

23.1 Three Pillars

Logging: Structured JSON via structlog. Fields: timestamp, level, module, trace_id, message, duration_ms. No file logging in containers.

Metrics: OpenTelemetry export. Key metrics: objective_compile_duration, plan_generate_count, decision_approval_latency, llm_request_duration, llm_token_usage, module_health_status, memory_query_duration, active_objectives.

Tracing: OpenTelemetry OTLP with head-based sampling (10% P0, 100% errors). Export to Jaeger via OpenTelemetry Collector.

23.2 Audit Trail

All state-changing operations recorded in decision_log table: objective.created, plan.generated, organization.restructured, decision.approved/rejected, system.error.

23.3 Health Check Endpoints

GET /health          → {"status": "ok", "version": "2.0", "uptime_seconds": 3600}
GET /health/readiness → Database, Redis, LLM providers reachable?
GET /health/liveness  → App process alive?
GET /health/modules   → Status of each registered module
GET /health/providers → Status of each LLM provider

25. Security Architecture

Authentication: JWT via Supabase Auth. Refresh token rotation (7-day refresh, 1-hour access).

Authorization: Roles: Admin (full org), Manager (department), Viewer (read-only), Agent (system). Row-Level Security per organization.

Decision Authority: Recommend (auto, low-risk), Approve (manager, medium-risk), Execute (human, high-risk/strategic).

Data Protection: TLS 1.3 in transit, encryption at rest, audit logging for all state changes, API rate limiting per key (100/1000 req/min).
